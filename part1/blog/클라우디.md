# 함수형 프로그래밍 원정대 회고

이번 레벨1 기간 동안 함수형 프로그래밍 원정대에 참여했다.

함수형 프로그래밍은 예전에 『자바스크립트 닌자 비급』을 통해 간단히 접해본 적이 있다. 다만 학습한 지 시간이 꽤 지났기도 했고 당시에는 인풋 위주로만 훑었던 터라, 이번 원정대 활동을 통해 함수형 프로그래밍에 대해 다시 탐구해보게 되었다.

원정대는 『쏙쏙 들어오는 함수형 코딩』을 기준으로 진행됐다.

## 액션, 계산, 데이터

『쏙쏙 들어오는 함수형 코딩』은 액션, 계산, 데이터라는 개념을 제시한다.

용어만 들으면 생소하지만, 하나씩 뜯어보면 기존의 함수형 프로그래밍에서 말하는 개념과 크게 다르지 않다.

### 데이터

```js
const rooms = [
  { id: "ROOM-A", name: "루비룸", capacity: 4, pricePerHour: 1000 },
  { id: "ROOM-B", name: "자바룸", capacity: 8, pricePerHour: 2000 },
  { id: "ROOM-C", name: "파이썬룸", capacity: 12, pricePerHour: 3000 },
];
```

데이터는 그냥 데이터다. 무슨 말인가 싶겠지만, 데이터는 값 그 자체를 가리킨다.

책에서는 조금 더 엄밀하게 "이벤트나 사실을 기록한 것"이라고 정의한다.

그 자체로는 실행될 수 없고 부수 효과(사이드 이펙트)도 없다. 계산의 입력으로 사용되거나 계산의 결과이기도 하며, 액션이 읽거나 쓰는 대상이 된다.

### 계산

```js
function calcRentalFee(pricePerHour, hours) {
  return pricePerHour * hours;
}

calcRentalFee(1000, 3); // 3000
calcRentalFee(2000, 2); // 4000
calcRentalFee(1000, 3); // 3000
```

계산은 순수 함수, 즉 수학에서 말하는 함수에 해당한다.

같은 입력이면 언제나 같은 출력을 반환하고, 외부 세계에 아무런 영향도 주지 않는다.

덕분에 테스트하기 쉽고, 다른 계산과 조합하기도 쉽다.

### 액션

```js
let cartItems = [];

// 언제 호출하느냐에 따라 결과가 다름 (암묵적 입력)
function getCartCount() {
  return cartItems.length;
}

// 호출 횟수에 따라 결과가 달라짐, 호출할 때마다 외부 상태를 변경시킴 (암묵적 출력)
function addToCart(item) {
  const countItem = cartItems.push(item);
  console.log(countItem);
}
```

반대로 액션은 부수 효과를 일으키는 함수다.

책에서는 한 걸음 더 나아가 액션이 '시간에 의존한다'는 점을 강조한다. 언제 호출하느냐, 몇 번 호출하느냐에 따라 결과가 달라진다는 뜻이다.

예시 코드만으로는 이 특징이 잘 와닿지 않을 수 있다. 아래 코드를 보자.

```js
// 시나리오 A: 장바구니가 비어있을 때 호출
getCartCount(); // 0

addToCart({ name: "키보드", price: 50000 }); // 1
addToCart({ name: "마우스", price: 30000 }); // 2

// 시나리오 B: 물건을 담은 뒤 호출
getCartCount(); // 2
```

`getCartCount()`는 아무런 인자도 받지 않는데도 호출 시점에 따라 결과가 달라진다. 함수 바깥에 있는 `cartItems`를 읽고 있기 때문이다.

이처럼 매개변수를 통하지 않고 외부 값을 참조하는 입력을 **암묵적 입력**이라고 한다.

마찬가지로 `addToCart()`도 함수 바깥의 `cartItems`를 직접 변경하고, `console.log`로 출력을 남긴다.

이렇게 반환값을 거치지 않고 외부에 영향을 주는 출력은 **암묵적 출력**이라고 부른다.

함수형 프로그래밍에서는 매개변수와 반환값을 거치지 않는 입출력을 각각 암묵적 입력, 암묵적 출력이라 부른다.

## 액션의 불확실성

암묵적 입력과 출력이 있는 함수, 즉 액션은 본질적으로 불확실성을 품고 있다.

호출하는 시점과 횟수에 영향을 받고, 외부 세계의 값을 읽거나 변경하기 때문이다.

그래서 액션 하나를 제대로 이해하려면 그 함수와 연결된 외부 요소들까지 함께 파악해야 한다. 입력만으로 결과가 결정되는 계산과는 크게 다른 지점이다.

이런 액션은 코드를 읽기 어렵게 만들고, 테스트를 어렵게 하며, 예상치 못한 버그의 원인이 되곤 한다.

## 액션은 나쁠까?

이렇게만 들으면 액션은 백해무익한 것만 같다. 그렇다면 액션을 완전히 제거해야 할까?

결론부터 말하면 불가능하다. 간단한 웹 앱 하나를 떠올려보자.

```js
function fetchUserProfile() {
  return fetch("/api/me").then((r) => r.json());
}

function renderUserName(name) {
  document.querySelector("#username").textContent = name;
}

fetchUserProfile().then((user) => renderUserName(user.name));
```

서버와 통신해 데이터를 가져오는 일, 화면에 무언가를 그리는 일. 이 둘은 어떻게 해도 액션일 수밖에 없다.

외부 세계(네트워크, DOM)와 상호작용하는 순간 이미 암묵적 입력과 출력이 발생하기 때문이다.

계산만으로는 유저에게 아무것도 보여줄 수 없다.

그래서 함수형 프로그래밍은 액션을 제거하는 것을 목표로 하지 않는다. 대신 **액션 안에 숨어있는 계산을 분리해내고, 액션의 범위를 최소화**하는 방향으로 코드를 다듬어간다.

## 액션에서 계산 분리하기

앞서 살펴본 `addToCart()`로 돌아가 보자.

```js
let cartItems = [];

function addToCart(item) {
  const countItem = cartItems.push(item); // 암묵적 입력 + 암묵적 출력
  console.log(countItem); // 암묵적 출력
}
```

암묵적인 입력과 출력을 걷어내면 아래처럼 바꿀 수 있다.

```js
function addToCart(cart, item) {
  return [...cart, item];
}
```

`cart`를 매개변수로 받고, 새 배열을 반환한다.

이제 이 함수는 같은 입력에 항상 같은 출력을 돌려주는 계산이 되었다.

물론 변경된 함수로 인해 새롭게 추가되어야 하는 코드가 있지만, 이렇게 액션 안에 숨어있는 계산을 꺼내는 것만으로도 예측 가능한 코드의 영역은 눈에 띄게 넓어진다.

## 에러를 던지는 함수는 계산일까

페어 프로그래밍을 진행하며 결론이 쉽게 나지 않았던 부분이 있다.

페어였던 루멘과 나는 예약 인원이 방의 수용 인원을 넘지 않는지 확인하는 로직을 계산으로 분리하고자 아래와 같은 코드를 작성했다.

```js
function validateParticipantLimit(attendees, room) {
  if (attendees > room.capacity) {
    throw new Error("인원이 초과되었습니다. 최대 수용 인원: " + room.capacity + "명");
  }
}
```

`throw`는 `return`이 아니니 암묵적 출력이 아닌가 하는 생각이 잠깐 스치긴 했지만,

입력이 같으면 언제나 결과가 같으니 계산이 맞다고 판단했고, 해당 함수를 계산으로 보기로 합의했다.

그리고 며칠 뒤 페어 프로그래밍을 마치고 피드백을 주고받는 자리에서 이 주제를 꺼냈다.

대부분의 크루들도 동일한 입력에 동일한 결과가 나오니 계산으로 보는 쪽이 합당하다는 생각을 가지고 있었다.

그런데 이 이야기를 나누던 중 나는 또 다른 생각이 들었다.

`throw`된 에러는 어디선가 잡아 처리하기 전까지 계속 상위로 전파된다. 그렇다면 외부 세계에 영향을 주는 셈이니 액션이라고 볼 수도 있지 않을까?

이런 생각을 원정대 크루들과 공유했고 그런 관점에서 생각해보니 또 액션처럼 보인다는 반응을 보였다.

이 글을 읽고 있는 독자는 어떻게 생각하는지 궁금하다, 에러를 던지는 함수는 계산일까 액션일까?

사실 이 질문은 정답이 있다. 한번 스스로 생각해본 뒤, `throw 순수 함수`라는 키워드를 검색해 확인해보길 권한다.

## 상수를 참조하는 함수는 계산일까

페어 프로그래밍을 하며 화두가 됐던 주제가 또 하나 있었다.

바로 상수를 참조하는 함수다.

```js
const MAX_CART_SIZE = 10;

function isCartFull(cart) {
  return cart.length >= MAX_CART_SIZE;
}
```

`isCartFull()` 입장에서 `MAX_CART_SIZE`는 외부 변수다. 엄밀히 말하면 암묵적 입력이고, 따라서 이 함수는 액션이 된다.

다만 `MAX_CART_SIZE`는 `const`로 선언되어 변경될 수 없기 때문에 호출 시점이나 호출 횟수의 영향을 받지 않는다.

그렇다면 계산으로 봐도 괜찮지 않을까?

한편으로는 이런 생각도 들었다.

상수로 분리해두는 것이 단순히 공통 값을 하나로 분리해둔 것으로 볼 수도 있지만, 반대로 **나중에 바꾸기 위해 분리해둔 것**이라고 볼 수도 있지 않을까?

`MAX_CART_SIZE`는 지금은 10이지만, 기획이 바뀌면 20이 될 수도 있다.

만약 `MAX_CART_SIZE`가 데이터가 아니라 함수라면 또 어떨까?

```js
function getMaxCartSize() {
  return 10;
}

function isCartFull(cart) {
  return cart.length >= getMaxCartSize();
}
```

이렇게 되면 함수형 프로그래밍 관점에서 `isCartFull()`은 계산으로 분류된다.

### 참조 투명성

[참조 투명성](https://ko.wikipedia.org/wiki/%EC%B0%B8%EC%A1%B0_%ED%88%AC%EB%AA%85%EC%84%B1)

이 고민을 정리하려면 참조 투명성이라는 개념을 빌려올 필요가 있다.

함수 호출을 그 결괏값으로 치환해도 프로그램의 의미가 달라지지 않는다면, 그 함수는 참조 투명하다고 말한다. 같은 입력에 같은 출력이 나오고 부수 효과가 없다는 계산의 조건을, 조금 더 엄밀한 언어로 표현한 것이다.

이 관점에서 `isCartFull()`을 다시 보자.

`MAX_CART_SIZE`가 `const`인 한, 한 번의 프로그램 실행 안에서 이 함수는 참조 투명하다.

`isCartFull(cart)`를 그 결괏값으로 치환해도 프로그램은 똑같이 동작한다.

즉, 계산이라 불러도 무방하다는 뜻이다.

## 분류는 목적이 아니라 수단

여기서 우리는 함수형 프로그래밍의 본질을 다시 짚어볼 필요가 있다.

함수형 프로그래밍이 계산과 액션을 구분하는 이유는 라벨을 붙이기 위함이 아니다.

예측 가능한 코드의 영역을 최대한 넓히고, 예측 불가능한 코드의 영역을 최대한 좁히기 위함이다.

계산은 추론하기 쉽고, 테스트하기 쉬우며, 조합하기도 좋다. 반면 액션은 그렇지 않다.

그래서 우리는 액션을 시스템의 가장자리로 밀어내고, 핵심 로직을 계산으로 채우려 한다.

이 관점에서 "`isCartFull()`이 계산인가 액션인가"라는 질문은 사실 본질이 아니다.

진짜로 물어야 할 것은 "이 함수가 얼마나 예측 가능한가, 얼마나 테스트하기 쉬운가, 얼마나 조합 가능한가"이다.

계산과 액션의 구분은 그 판단을 돕기 위한 수단일 뿐이다.

## 마치며

함수형 프로그래밍 원정대 활동은 흐릿하고 파편적으로 남아있던 함수형 프로그래밍의 개념들을 다시 또렷이 정리할 수 있는 좋은 계기가 되었다.

가장 인상 깊었던 건 페어 프로그래밍이었다. 페어와 머리를 맞대고 고민을 나누는 시간도 즐거웠지만, 무엇보다 같은 문제를 저마다의 방식으로 풀어내는 팀들의 모습을 지켜볼 수 있었다는 점이 흥미로웠다. 어느 팀은 계층형 설계로 접근했고, 또 어느 팀은 액션을 모두 계산으로 분리한 뒤 별도의 컨트롤러를 두기도 했다.

혼자 책을 읽거나 단순히 함께 읽는 데 그쳤다면 얻지 못했을 인사이트들이었다.

원정대에서 스터디로 전환하며 힘을 빼기로 했지만, 이런 활동을 앞으로도 꾸준히 이어갈 수 있으면 좋겠다.
