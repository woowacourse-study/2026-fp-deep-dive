## SRP, 관심사 분리 그리고 함수형 프로그래밍

우테코 프리코스부터 레벨1까지 각종 미션을 해오다 보니 반복적으로 들어오던 말이 있다.

- 하나의 함수는 하나의 일만 해야 한다.
- 단일 책임 원칙(SRP): 하나의 모듈은 오직 하나의 변경 이유만을 가져야 한다.
- 관심사 분리

레벨1 로또 미션을 리팩토링하면서 가장 강조됐던 것도 바로 이것들이었다.

'관심사 분리'

중요한 것 같기는 한데, 로또 step1 미션을 마무리할 때까지만 해도 크게 와닿지 않았다. 하지만 step2에서 콘솔 환경의 코드를 웹 환경으로 전환하면서 그 이유를 체감할 수 있었다.
도메인과 View 관심사 분리가 잘 되어있던 덕에 step1에서 구현했던 도메인 로직을 단 한줄도 건드리지 않고 웹 UI로 갈아끼울 수 있었던 것이다.


미션을 수행하며 스스로 정의 내려 본 관심사 분리는 다음과 같다.

> 관심사 분리란, 
각 코드(함수, 모듈, 레이어)가 자신이 맡은 역할에만 집중하도록 책임을 나누는 것이다.

각 함수의 관심사에 따라 코드를 잘 분리해놓으면 어떤 코드를 변경할 때 오직 하나의 변경 이유만을 갖게 된다. 
즉, 하나의 변경 사항이 **다른 곳에 영향을 주지 않는다.**
로또 미션에서 UI를 갈아끼웠을 때 도메인 로직이 무사했던 이유가 바로 이것이다.


<br/>
<br/>


로또 미션 요구사항에는 프리코스 때와는 또 다른 새로운 항목이 있었다.

![](https://velog.velcdn.com/images/vlmbuyd/post/9c9522f2-99ec-4ce9-9f7f-1e464ae35971/image.png)

**부수 효과를 분리하고, 순수함수를 활용하여 예측 가능하게 코드를 작성한다**


당시 함수형 프로그래밍 원정대를 하고 있었기에 이것이 "함수형 프로그래밍을 활용하여 코드를 작성하라"는 요구사항임을 바로 알아챌 수 있었다.

미션을 수행하면서 관심사를 분리하는 것과 함수형으로 코드를 개선해나가는 과정이 묘하게 닮아있는 것 같다는 느낌이 들었다.

> 관심사 분리를 잘 해놓으면 하나의 변경 사항이 **다른 곳에 영향을 주지 않는다.**
함수형 프로그래밍 또한 외부 세계에 영향을 주는 '부수 효과'를 통제하기 위해 노력한다.

방향은 비슷해 보이는데, 둘은 정말 같은 의미일까? 
어떤 점이 다른 걸까?
아니면 서로 다른 축에서 같은 목표를 향하는 걸까.


이 글은 이 물음표들로부터 출발한다.
먼저 관심사 분리를 직접 적용해보고, 그 과정에서 생기는 한계를 FP 개념으로 채워나가는 방식으로 풀어보려 한다.

## 관심사 분리해보기

아래 코드를 보자. 회원을 등록하는 `registerMember` 함수다.

```js
let currentMember = null;

// [액션]
function registerMember(id, name, points) {
  if (!id || !name) {
    console.log("아이디와 이름은 필수입니다.");
    return;
  }
  currentMember = { id, name, points, grade: "normal", totalUsageHours: 0 };
  currentMember.points -= 10;  // 가입비 차감
  currentMember.grade = currentMember.points >= 100 ? "honor" : "normal"; // 등급 계산
  console.log(name + "님이 등록되었습니다. 등급: " + currentMember.grade);
}

registerMember("M001", "유월", 110);

```

이 함수가 하는 일을 나열해보면 다음과 같다.

1. 유효성 검사
2. 멤버 객체 생성
3. 포인트 차감
4. 등급 계산
5. 상태 변경 (전역변수)
6. 콘솔 출력

6가지 관심사가 한 함수에 뭉쳐있다. 관심사 분리 원칙에 따라 각 책임을 나눠보자.

```js
let currentMember = null;

// 유효성 검사
function isValidInput(id, name) {
  return Boolean(id && name);
}

// 멤버 객체 생성
function createMember(id, name, points) {
  return { id, name, points, grade: "normal", totalUsageHours: 0 };
}

// 포인트 차감
function usePoints(member, amount) {
  member.points -= amount;
  return member;
}

// 등급 계산
function calcGrade(member) {
  member.grade = member.points >= 100 ? "honor" : "normal";
  return member;
}

// 콘솔 출력
function printRegisterResult(member) {
  console.log(member.name + "님이 등록되었습니다. 등급: " + member.grade);
}

// 프로세스 조율
function registerMember(id, name, points) {
  if (!isValidInput(id, name)) {
    console.log("아이디와 이름은 필수입니다.");
    return;
  }
  currentMember = calcGrade(usePoints(createMember(id, name, points), 10));
  printRegisterResult(currentMember);
}
```

각 함수가 하나의 일만 한다. 
`registerMember`는 이제 직접 "무언가를 처리"하지 않고, 각 함수에 일을 위임하며 흐름만 조율한다.

관심사 분리 기준으로는 통과처럼 보인다. 그런데 뭔가 찜찜하다.

`calcGrade`를 단독으로 테스트해보자. 

```js
const member = { name: "조앤", points: 110, grade: "normal" };

calcGrade(member);

console.log(member.grade); // "honor" ← 함수 밖에서 원본이 바뀌어 있음
```

함수를 호출했을 뿐인데 바깥의 `member`가 몰래 바뀌었다. 
관심사를 하나로 줄였는데도 이 찜찜함은 왜 생기는 걸까. 
관심사 분리만으로는 설명이 안 되는 무언가가 있다.



## 함수형 프로그래밍(Functional Programming)

이 찜찜함의 정체를 함수형 프로그래밍(Functional Programming, 이하 FP) 개념으로 설명할 수 있다.

FP를 사전적으로 정의하면 다음과 같다.

함수형 프로그래밍(函數型 프로그래밍, 영어: functional programming)은 자료 처리를 수학적 함수의 계산으로 취급하고 상태와 가변 데이터를 멀리하는 프로그래밍 패러다임의 하나이다. 
출처: [위키백과](https://ko.wikipedia.org/wiki/%ED%95%A8%EC%88%98%ED%98%95_%ED%94%84%EB%A1%9C%EA%B7%B8%EB%9E%98%EB%B0%8D)

말이 너무 어렵다. 
내가 이해한 방식대로 조금 더 쉽게 풀어 정의를 내려보면 다음과 같다.

> 순수 함수(수학 함수)를 지향하고
부수 효과(side effect)를 최소화하여 격리하며
데이터의 불변성을 원칙으로 삼는 프로그래밍 패러다임

"순수 함수, 부수효과, 불변성"

위 세 가지 키워드만 제대로 알고 넘어간다면 FP 절반 이상은 이해했다고 볼 수 있다.

<br/>

### 데이터, 계산, 액션

FP에서는 코드를 데이터, 계산, 액션 세 가지로 분류한다.

<br/>

**데이터**

```js
const menus = [
  { name: "자장면", price: 7000},
  { name: "깐쇼새우", price: 12000},
];
```

그 자체로 실행되지 않는 값이다.
우리가 흔히들 사용하는 숫자, 문자열, 배열 등을 생각하면 된다.


<br/>

**계산(순수 함수)**

같은 입력값을 넣으면 항상 동일한 결과를 반환하는 함수를 계산(순수 함수)이라고 한다.

아래 코드 예제에서 `getPossibleMenus` 함수는 
현재 가지고 있는 돈(`money`)과 메뉴(`menus`)를 인자로 받아 
구매 가능한 메뉴 리스트를 필터링해주는 '계산' 함수다.

```js
// 데이터
const menus = [
  { name: "짜장면", price: 7000},
  { name: "깐쇼새우", price: 12000},
];

// 계산
function getPossibleMenus(money, menus) {
  	return menus.filter(menu => menu.price <= money);
}

getPossibleMenus(8000, menus);  // [{ name: "짜장면", price: 7000}]
getPossibleMenus(8000, menus);  // [{ name: "짜장면", price: 7000}]
```

함수 호출부를 보면 알수 있다시피 같은 입력값을 몇 번 넣더라도 항상 같은 결과를 반환한다.
즉, 계산은 호출 시점과 호출 횟수에 영향을 받지 않는다.
그저 입력 받은 값으로부터 출력할 값을 순수하게 반환할 뿐이다.

<br/>

**액션**

부수 효과가 존재하는 함수를 액션이라고 한다.

`부수효과`란?
함수가 외부 세계에 영향을 주는 것을 말한다.

즉, 외부 세계에 영향을 주는 함수를 액션이라고 한다.
액션은 순수하지 않다.

```js
let orderCount = 0;

// 계산
function order(menuName) {
  	orderCount++;
  	console.log(`${menuName} 주문완료! (${orderCount}번 째)`);
}

order("짜장면");  // "짜장면 주문완료! (1번 째)
order("짜장면");  // "짜장면 주문완료! (2번 째)
```

`order` 함수는 호출될 때마다 `orderCount`에 영향을 주고 있다.
따라서 동일한 입력값이 입력되더라도 다른 결과를 반환하게 된다.
즉, 액션은 호출 시점과 호출 횟수에 의존한다.

<br/>

또한 액션은 **전염성**이 있어 코드 전체로 퍼진다.
어떤 함수 안에 액션이 하나만 있어도 그 함수 전체가 액션이 된다.

```js
let orderCount = 0;

// 액션
function order(menuName) {
  orderCount++;
  console.log(`${menuName} 주문완료! (${orderCount}번 째)`);
}

// 액션
function orderAndGetReceipt(menuName, price) {
  order(menuName);  // ❌ 액션을 호출하기 때문에 부모 함수도 액션이 된다.
  return `${menuName} / ${price}원`;
}

// 액션
function processOrder(menuName, price) {
  const receipt = orderAndGetReceipt(menuName, price);  // ❌ 마찬가지
  return receipt;
}
```

`orderAndGetReceipt`는 인자를 받아 문자열을 반환하니 계산처럼 보인다. 하지만 내부에서 액션인 `order`를 호출하는 순간 이 함수도 액션이 된다. 그리고 `orderAndGetReceipt`를 호출하는 `processOrder`도 마찬가지다.

액션은 이렇게 호출 체인을 타고 위로 전염된다.


<br/>


결론적으로 FP는 외부 세계에 영향을 주기에 통제가 어려운 액션보다
코드의 예측 가능성과 테스트 용이성을 높여주는 계산을 지향한다.

## 관심사 분리 + FP 같이 적용해보기

이제 FP 개념을 손에 쥐고, 아까의 코드로 돌아가보자.

관심사를 분리한 뒤 찜찜했던 부분이 기억나는가.
바로 이 함수다.

```js
function calcGrade(member) {
  member.grade = member.points >= 100 ? "honor" : "normal"; // ❌ 암묵적 출력: 객체 원본을 직접 수정
  return member;
}
```
관심사 분리는 **"무엇을 하는가"**를 기준으로 함수를 나눈다. 
`calcGrade`는 "등급 계산"이라는 하나의 관심사만 갖는다. 여기까지는 통과다.

그런데 FP는 추가로 **"어떻게 하는가"**를 따진다. 
`calcGrade`는 외부에서 넘겨받은 `member` 객체를 직접 수정하고 있다. 
이것이 암묵적 출력이고, 이 함수를 액션으로 만드는 원인이다.


### 암묵적 입출력을 명시적으로

액션을 계산으로 만들기 위해서는 암묵적 입출력을 제거하여 명시적 입출력으로 만들어야 한다. 
암묵적 입출력이 부수효과를 일으키기 때문이다.


암묵적 출력은 `return` 값으로 대체하여 명시적 출력으로 바꾸는 것이 원칙이다. 
이때 원본을 직접 수정하는 대신 새 객체를 만들어 반환하는 것을 **카피온라이트(copy-on-write)**라 하며, 이것이 FP의 핵심 개념인 **불변성**이다.

```js
// [계산]: 카피온라이트로 원본 보존
function calcGrade(member) {
  const grade = member.points >= 100 ? "honor" : "normal";
  return { ...member, grade }; // 명시적 출력: 새 객체 반환 
}
```
달라진 점을 직접 확인해보자.

```js
const member = { name: "조앤", points: 110, grade: "normal" };

const graded = calcGrade(member);

console.log(member.grade);  // "normal" ← 원본 보존
console.log(graded.grade);  // "honor"  ← 새 객체에만 반영
```

이전에는 `calcGrade(member)`를 호출하는 것만으로 함수 외부의 `member`가 몰래 바뀌었다. 이제는 원본은 그대로고, 변경된 결과는 새 객체로 반환된다. 
함수를 호출한 쪽에서 결과를 어떻게 쓸지 직접 결정할 수 있게 된 것이다.

"등급 계산"이라는 같은 관심사를 가진 함수이지만, 
FP 원칙 충족했느냐에 따라 코드의 예측 가능성이 달라진다.

<br/>

마찬가지로 `usePoints`도 원본을 수정하고 있었다.

```js
// [액션] 
function usePoints(member, amount) {
  member.points -= amount; // ❌ 암묵적 출력: 객체 원본 직접 수정 
  return member;
}

// [계산]: 카피온라이트 적용
function usePoints(member, amount) {
  return { ...member, points: member.points - amount }; // 명시적 출력: 새 객체 반환 
}
```

<br/>

```js
function printRegisterResult(member) {
  console.log(member.name + "님이 등록되었습니다. 등급: " + member.grade);
}
```
`printRegisterResult`는 최소 단위로 분리했지만 여전히 액션이다. 
`console.log`가 외부 세계에 영향을 주고 있기 때문이다. 
이런 액션 함수는 계산으로 바꾸는 대신 예측 가능한 곳으로 격리한다.

<br/>

**완성된 코드**

```js

// [계산]
function isValidInput(id, name) {
  return Boolean(id && name);
}

// [계산]
function createMember(id, name, points) {
  return { id, name, points, grade: "normal", totalUsageHours: 0 };
}

// [계산]: 카피온라이트
function usePoints(member, amount) {
  return { ...member, points: member.points - amount };
}

// [계산]: 카피온라이트
function calcGrade(member) {
  const grade = member.points >= 100 ? "honor" : "normal";
  return { ...member, grade };
}




// [액션]: 격리
function printRegisterResult(member) {
  console.log(member.name + "님이 등록되었습니다. 등급: " + member.grade);
}

// [액션]: 프로세스 조율 + 상태 변경은 여기서만
function registerMember(id, name, points) {
  if (!isValidInput(id, name)) {
    console.log("아이디와 이름은 필수입니다.");
    return;
  }
  currentMember = calcGrade(usePoints(createMember(id, name, points), 10));
  printRegisterResult(currentMember);
}

registerMember("M001", "조앤", 110);
console.log(currentMember.points); // 100
console.log(currentMember.grade);  // "honor"
```


<br/>

## 좋은 함수란 무엇인가

지금까지의 흐름을 정리해보자.

관심사 분리를 먼저 적용했을 때, 함수를 6개로 나누는 데는 성공했다.
하지만 나눈 함수 중 일부(`calcGrade`, `usePoints`)가 원본을 직접 수정하고 있었다.
관심사 분리 기준만으로는 이 문제를 잡아낼 수 없었다.

FP 렌즈를 끼고 바라보자 비로소 문제가 보였다.
"관심사를 나눴는가"에서 더 나아가 "나눈 함수가 진짜 계산인가"를 따져야 했다.


관심사 분리는 **책임의 경계**를 기준으로 함수를 나누고, 
FP는 **부수 효과의 통제**를 기준으로 제약을 건다. 

다시 말해, 관심사 분리가 "이 함수가 하는 일이 하나인가" 를 묻는다면, 
FP는 "이 함수가 외부 세계에 영향을 주지 않는가" 를 묻는다.

둘은 서로 다른 축에서 같은 목표를 향하는 교집합이다. 

관심사를 나눴어도 불변성을 어기면 FP 원칙에 어긋나고, 
불변성을 지켜도 관심사가 뭉쳐있을 수 있다. 

두 질문을 동시에 통과한 함수만이 테스트가 용이하고 예측가능한 독립적인 함수가 된다.
그리고 그런 함수를 만드는 것이, 좋은 코드에 한 걸음 가까워지는 방법이라고 생각한다.
