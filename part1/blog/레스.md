## 함수형프로그래밍

**액션, 계산, 데이터: 코드를 세 가지로 보기 시작하면 달라진다.**

함수형 프로그래밍은 생각보다 단순하게 시작한다. 일단 모든 코드를 세 가지로 분류하는 것이다. 그 이후 테스트가 쉬운, 순수성이 보장되는 함수를 최대한 많이 확보하는 전략이라고 이해하면 된다.

**데이터**는 그냥 값이다. 숫자, 문자열, 배열, 객체같이 아무 동작도 하지 않고, 사실을 담고 있을 뿐이다.

```
const rooms = [
  { id: "ROOM-A", name: "루비룸", capacity: 4, pricePerHour: 1000 },
  { id: "ROOM-B", name: "자바룸", capacity: 8, pricePerHour: 2000 },
];
```

**계산**은 같은 입력에 항상 같은 출력이 나오는 함수이다. 호출 시점이 언제든, 몇 번을 호출하든 결과가 동일하다. 그래서 계산은 테스트하기가 쉽다. 입력을 넣고 출력을 확인하면 끝이고, 외부 상태를 신경 쓸 필요가 없다.

```
function calculateFee(pricePerHour, duration) {
  return pricePerHour * duration;
}

calculateFee(1000, 2); // 항상 2000
```

**액션**은 호출 시점이나 횟수에 따라 결과가 달라지는 함수이다. 전역 변수를 바꾸거나, API를 호출하거나, 콘솔에 출력하는 것이 모두 액션이다. 액션 자체가 나쁜 건 절대 아니다. 프로그램에서 액션은 반드시 존재할 수 밖에 없다.

```
function registerMember(id, name, point) {
  currentMember = createMember(id, name, "normal", point, 0); // 전역 변경
  reservations = [];                                          // 전역 변경
  console.log(`${name}님이 등록되었습니다`);                       // 외부 출력
}
```

문제는 **액션과 계산이 한 함수에 섞여있을 때**에 발생한다.

**\-**

**암묵적 입출력 vs 명시적 입출력**

액션 함수를 계산으로 만드는 가장 확실한 방법은 암묵적 입출력을 명시적으로 바꾸는 것이다.

암묵적 입력은 함수가 인자 외의 것을 읽는 것이다. 전역 변수, 외부 상태, this 같은 것들이 해당된다. 암묵적 출력은 리턴값 외의 것을 바꾸는 것이다. 전역 변수 변이, 콘솔 출력, DOM 조작이 여기 해당한다.

```
// 암묵적 입력 — gradeConfig를 전역에서 읽음
function getGrade(hours) {
  if (hours >= gradeConfig.master.minHours) return "master";
  if (hours >= gradeConfig.vip.minHours) return "vip";
  return "normal";
}

// 명시적 입력 — 인자로 받음
function getGrade(hours, gradeConfig) {
  if (hours >= gradeConfig.master.minHours) return "master";
  if (hours >= gradeConfig.vip.minHours) return "vip";
  return "normal";
}
```

전역에서 읽으면 gradeConfig가 어디선가 바뀔 때 결과가 달라질 수 있다. 인자로 받으면 같은 입력에 항상 같은 출력이 보장된다. 테스트할 때도 원하는 gradeConfig를 직접 넣어볼 수 있어서 편하다. 스터디에서는 이 지점에서 논의가 가장 많이 나왔다.

_gradeConfig가 사실상 상수라면 굳이 인자로 받아야 하나? vs 그래도 원칙적으로 명시적이 낫다_

결론은 팀마다 달랐다. 나는 후자가 맞다고 생각한다. 지금은 상수처럼 보여도 언제 바뀔지 모르고, 무엇보다 명시적인 코드는 읽는 사람이 함수 밖을 뒤질 필요가 없다. 그 고민 자체가 함수형 사고의 핵심이라고 생각한다.

\-

**함수형 사고는 "이 함수가 몰래 뭔가를 읽거나 바꾸고 있지는 않은가?"를 항상 의심하는 데서 시작한다.** 암묵적 출력도 마찬가지다.

```
// 암묵적 출력 — 전역 배열을 직접 변이
function addReservation(reservation) {
  reservations.push(reservation);  // 리턴값 없이 전역을 바꿈
}

// 명시적 출력 — 새 배열을 리턴
function addReservation(reservations, reservation) {
  return [...reservations, reservation];
}
```

아래는 호출한 쪽이 리턴값을 쓸지 말지 결정한다. 함수 자체는 아무것도 모르는 채로 계산만 한다. 이 작은 차이가 쌓이면 코드베이스 전체의 신뢰도가 달라진다.

**\-**

**불변성과 카피-온-라이트, 그리고 방어적 복사**

함수형에서 불변성은 빠질 수 없다. 원본 데이터를 건드리지 않고, 바꿀 일이 있으면 복사본을 만들어서 복사본을 수정한다.

```
// 원본을 직접 변이
function updatePoints(member, points) {
  member.points += points; // 원본이 바뀌어버림
}

// 카피-온-라이트
function updatePoints(member, points) {
  const newMember = { ...member };
  newMember.points += points;
  return newMember;
}
```

원본을 직접 바꾸면 그 객체를 참조하는 모든 곳에 영향이 간다. 어디서 값이 바뀌었는지 추적하기 어렵다. 카피-온-라이트를 쓰면 이 함수가 원본을 건드렸는지 걱정을 할 필요가 없다.

그런데 여기서 한 가지 함정이 있다. 중첩 객체를 얕은 복사하면 안심할 수 없다.

```
const member = {
  name: "less",
  address: { city: "anyang" }
};

const newMember = { ...member };
newMember.address.city = "seoul"; // 원본 member.address.city도 바뀐다!
```

...member는 1단계만 복사한다. address는 여전히 같은 참조를 가리킨다.

이걸 해결하려면 깊은 복사가 필요하다.

```
const newMember = {
  ...member,
  address: { ...member.address }
};
```

중첩이 깊어지면 이런 행동이 번거로워진다. 그래서 등장하는 개념이 **방어적 복사**이다. 신뢰할 수 없는 코드와 데이터를 주고받을 때, 경계면에서 깊은 복사를 해두는 것이다.

```
// 외부 라이브러리나 레거시 코드에 데이터를 넘길 때
function sendToLegacySystem(data) {
  const deepCopy = JSON.parse(JSON.stringify(data)); // 깊은 복사
  legacySystem.process(deepCopy); // 원본은 안전
}
```

JSON.parse(JSON.stringify(...)) 는 간단하지만 함수나 undefined가 포함된 객체에선 쓸 수 없다. 실무에선 structuredClone()이나 lodash의 cloneDeep을 쓰는 경우가 많다고 한다.

즉, 카피-온-라이트는 내가 통제할 수 있는 코드 안에서의 불변성이고, 방어적 복사는 통제할 수 없는 경계면에서의 불변성이다. 둘을 구분해서 쓰는 게 핵심이다.

**\-**

**계층형 설계는 분리하다 보면 자연스럽게 생기는 구조**

함수를 분리하다 보면 계층이 생긴다.

```
Layer 4 (비즈니스 로직)   makeReservation, cancelReservation
Layer 3 (도메인 계산)     calculateEarnedPoints, getConfirmedReservations
Layer 2 (범용 유틸)       findById, replaceById, filterByKey
Layer 1 (JS 문법)        Array.filter, spread 연산자
```

아래로 갈수록 재사용성이 높다. findById는 룸이든 예약이든 어떤 배열에나 쓸 수 있다. makeReservation은 이 시스템에서만 의미 있다. 여기서 계층형 설계의 핵심 규칙은 **아래 계층은 위 계층을 모르도록 설계하는 것**이다**.** 

findById는 자기가 예약을 찾는 데 쓰이는지 룸을 찾는 데 쓰이는지 모른다. Array.filter는 filterByKey가 자기를 쓰는지도 모르기 때문에 안심하고 재사용할 수 있다.

변경이 생겼을 때도 영향 범위가 명확하다. Layer 2 유틸을 바꾸면 Layer 3, 4가 영향을 받을 수 있다. 반대로 Layer 4 비즈니스 로직을 바꿔도 Layer 1, 2는 전혀 영향을 받지 않는다. 변경이 위에서 아래로만 흐르기 때문이다.

여기서 주의할 점이 있다. 계층을 나눈다고 무조건 파일을 분리하거나 폴더를 만들 필요는 없다. 중요한 건 물리적 분리가 아니라 의존 방향이다. 이 함수가 위 계층 개념을 알고 있지는 않은지 의식하는 것만으로도 코드 구조가 달라진다.

**\-**

**함수형 vs 객체지향**

함수형과 객체지향은 사실 대립하는 개념이 아니고, **둘 다 결국 클린코드를 향한 서로 다른 방법론**이라는 느낌이 들었다.

객체지향은 상태와 행동을 함께 묶는다. 객체가 자신의 상태를 관리하고, 메서드를 통해 외부와 소통한다. 복잡한 도메인을 모델링할 때 강력하다. 예약 시스템에서 Reservation 객체가 자신의 상태 변화를 직접 책임지는 방식이 자연스럽게 느껴지는 건 그래서이다.

함수형은 반대다. 상태와 행동을 분리한다. 데이터는 그냥 값이고, 함수는 그 값을 받아서 새 값을 리턴할 뿐이다. 객체가 상태를 들고 다니는 대신, 데이터가 함수를 통해 흘러간다. 부수 효과를 최소화하기 때문에 테스트가 쉬워지고, 데이터의 흐름이 눈에 잘 보인다.

실무에서는 대부분 섞어 쓴다. React가 좋은 예다. 컴포넌트는 객체지향적으로 설계되지만, 상태 변환 로직은 함수형으로 작성하길 권장한다. useState의 setter에 함수를 넘기는 것과, useReducer의 reducer가 순수 함수여야 하는 것이 그 흔적이다.

```
// 객체지향적 접근 — 객체가 자신의 상태를 변경
class ShoppingCart {
  addItem(item) {
    this.items.push(item); // 내부 상태 직접 변이
  }
}

// 함수형 접근 — 새로운 값을 리턴
function addItem(cart, item) {
  return { ...cart, items: [...cart.items, item] };
}
```

어느 쪽이 더 나은가는 맥락에 따라 다르다고 생각한다.

중요한 건 두 가지를 모두 이해하고, 지금 풀려는 문제에 어떤 사고방식이 더 맞는지 판단할 수 있는 것이다. 스터디에서 객체지향으로 짜놓은 코드를 함수형으로 리팩토링해보니, 이전에 보이지 않던 것들이 보이기 시작했다. 어디서 상태가 암묵적으로 바뀌는지, 어느 함수가 사실 테스트하기 어려운 구조인지. 함수형의 렌즈로 코드를 보는 것 자체가 좋은 훈련이었다.

이 함수가 액션인지 계산인지를 의식하기 시작하면 코드 짜는 방식이 확실히 달라진다. 즉, 뭘 분리해야 하는지, 뭘 인자로 받아야 하는지, 뭘 리턴해야 하는지가 명확해진다.

객체지향에 질리셨다면 한번 학습 해보시길. 생각보다 재밌다.
